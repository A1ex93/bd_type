- Реляционные СУБД обеспечивают строгую целостность данных, транзакционность и поддержку аналитических функций (оконные функции, агрегации).

3.1. Пять преимуществ SQL-систем перед NoSQL

Четкая структура данных (строгая схема, типы данных, ограничения)
Гарантия целостности данных (ACID-транзакции, внешние ключи)

Универсальность (подходит для большинства бизнес-задач)

3.1. Преимущества NewSQL перед SQL и NoSQL*

Масштабируемость как у NoSQL (горизонтальное масштабирование)
ACID-транзакции как у SQL (целостность данных)
Высокая производительность (оптимизация для распределенных систем)
Гибкость (поддержка и SQL-запросов, и NoSQL-подходов)
Упрощенный переход (совместимость с SQL-синтаксисом)

### **Выбор СУБД и модели распределённых вычислений для 1000 машин**  

#### **Критерии выбора СУБД:**  
1. **Горизонтальная масштабируемость**  
   - СУБД должна эффективно распределять данные и запросы на 1000 узлов без деградации производительности.  
2. **Поддержка распределённых транзакций**  
   - Если нужна строгая согласованность (ACID), подойдут **NewSQL (CockroachDB, Google Spanner)**.  
   - Если допустима eventual consistency — **NoSQL (Apache Cassandra, ScyllaDB)**.  
3. **Тип нагрузки**  
   - **OLTP** (много коротких транзакций) → **NewSQL или Sharded PostgreSQL**.  
   - **OLAP** (аналитика, сложные запросы) → **ClickHouse, Apache Druid**.  
4. **Локализация данных**  
   - Если данные географически распределены — **глобально-распределённые СУБД (Spanner, YugabyteDB)**.  

#### **Лучшая модель распределённых вычислений:**  
**Модель: Shared-Nothing Architecture**  
- Каждая машина независима (свой CPU, RAM, диск).  
- Данные шардируются между узлами (например, по диапазону ключей).  
- **Почему подходит:**  
  - Максимальная параллелизация вычислений.  
  - Отказоустойчивость (падение одного узла не убивает кластер).  
  - Линейное масштабирование при добавлении машин.  

#### **Оптимальные технологии:**  
1. **Для OLTP:**  
   - **CockroachDB** (NewSQL): SQL-синтаксис + автоматический шардинг.  
   - **ScyllaDB** (NoSQL): высокая скорость записи/чтения.  
2. **Для OLAP:**  
   - **ClickHouse**: колоночное хранение, агрегация в реальном времени.  
   - **Apache Spark + Parquet**: для пакетной обработки.  

#### **Архитектура решения (пример):**  
1. **Шардинг данных**  
   - Таблицы делятся по ключу (например, `user_id % 1000`).  
2. **Распределённые запросы**  
   - Запрос `SELECT * FROM logs WHERE date > '2024-01-01'` выполняется параллельно на всех узлах.  
3. **Репликация**  
   - Каждый шард реплицируется на 2–3 машины для отказоустойчивости.  

#### **Почему не подходят:**  
- **Классические SQL (MySQL, PostgreSQL)**:
  - Требуют ручного шардинга, не масштабируются линейно.  
- **Pure NoSQL (MongoDB)**:
  - Нет распределённых JOIN и транзакций.  

**Итог:**  
Для 1000 машин лучший выбор — **NewSQL (CockroachDB/Spanner)** или **специализированные OLAP-системы (ClickHouse)** с моделью **Shared-Nothing**. Это даст:  
- Автоматическое масштабирование.  
- Поддержку сложных запросов.  
- Отказоустойчивость.
